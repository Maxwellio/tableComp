================================================================================
BaseTreeTable — точечный патч под режим "грузим всё дерево сразу" (Вариант B)
================================================================================

Затронуто два файла:
  BaseTable/BaseTreeTable.tsx
  BaseTable/hooks/useFetchTreeData.tsx

Все изменения помечены в коде комментариями "Правка N." — нумерация совпадает
с этим файлом.

Цель: дерево приходит с бэкенда целиком (вложенный JSON), TanStack сам
разворачивает его на любую глубину через getSubRows. Ленивая догрузка детей
по клику больше не используется.


--------------------------------------------------------------------------------
ПРАВКА 1. Корень дерева и форма ответа сервера
--------------------------------------------------------------------------------
Файлы: BaseTreeTable.tsx, hooks/useFetchTreeData.tsx

Было:
    const {data, loading, setData, fetchChildren} = useFetchData<TData>(url, 1000242);
    ...
    export const useFetchData = <T,> (url:String, id:Number) => {
    ...
        const reqApi = `${url}/${id}`;
        setData(Array.of(data));
    ...
    }, []);

Стало:
    - в пропсы BaseTreeTable добавлен необязательный rootId?: number | string;
    - id 1000242 (запись конкретного проекта) убран из кода компонента;
    - без rootId запрос идёт на `${url}`, с rootId — на `${url}/${rootId}`;
    - Array.of(data) заменён на Array.isArray(data) ? data : [data];
    - зависимости useEffect: [] -> [url, rootId];
    - добавлен флаг cancelled в cleanup эффекта;
    - типы параметров String/Number -> string/number|string.

Почему:
    - захардкоженный id делал компонент непереиспользуемым — это первое, что
      мешало подключить его в другом проекте;
    - Array.of(data) поддерживал ровно один корень-объект. Если сервер отдаёт
      массив корней (лес — типичный случай для adjacency-list таблиц, где корни
      помечены parent = 0), получалось [[root1, root2]], то есть одна фиктивная
      строка, обёрнутая вокруг массива;
    - с пустым массивом зависимостей rootId читался бы только при монтировании,
      и смена пропса ничего бы не меняла;
    - cancelled нужен именно из-за появившихся зависимостей: при быстрой смене
      url/rootId ответ более старого запроса может прийти последним и затереть
      более свежие данные, плюс снимается setState после размонтирования.


--------------------------------------------------------------------------------
ПРАВКА 2. onExpandedChange — убрана ленивая догрузка и падение на "развернуть всё"
--------------------------------------------------------------------------------
Файл: BaseTreeTable.tsx

Было:
    onExpandedChange: (updater) => {
        const newExpanded = updater(expanded);
        Object.keys(newExpanded)
            .filter(id => newExpanded[id] && !expanded[id])
            .forEach(rowId => {
                const row = table.getRow(rowId);
                if (row.getCanExpand() && !row.original.children) {
                    fetchChildren(row.original.id);
            }});
        setExpanded(newExpanded);
    },

Стало:
    onExpandedChange: setExpanded,

Дополнительно: состояние expanded типизировано как ExpandedState
(useState<ExpandedState>({}) вместо useState({})), потому что TanStack кладёт
туда либо карту rowId -> boolean, либо булево true.

Почему:
    - при полностью загруженном дереве у каждого раскрываемого узла уже есть
      children, поэтому весь блок с fetchChildren не выполнялся никогда;
    - код падал: updater считался функцией всегда, а table.toggleAllRowsExpanded()
      передаёт в onExpandedChange голое значение true. Проверено на table-core
      8.21.3 — старый вариант даёт "TypeError: updater is not a function", новый
      отрабатывает и выставляет expanded = true;
    - сеттер useState сам различает функцию-апдейтер и готовое значение, поэтому
      одна строка полностью заменяет прежний блок.

Побочно: из деструктуризации useFetchData убраны setData и fetchChildren —
они больше не используются в компоненте. Сама функция fetchChildren в хуке
оставлена нетронутой на случай возврата к ленивому режиму.


--------------------------------------------------------------------------------
ПРАВКА 3. getRowCanExpand
--------------------------------------------------------------------------------
Файл: BaseTreeTable.tsx

Было:
    getRowCanExpand: row => row.original.hasChildren,

Стало:
    getRowCanExpand: row => row.original.hasChildren ?? row.subRows.length > 0,

Почему:
    TanStack вычисляет раскрываемость как
        getRowCanExpand?.(row) ?? (enableExpanding && !!row.subRows?.length)
    То есть при отсутствии поля hasChildren возвращался undefined и срабатывал
    дефолт по subRows — это работало. А вот hasChildren: false запрещало
    раскрытие даже у узла с реально загруженными детьми (false ?? x даёт false).
    При полной загрузке дерева источником истины должны быть subRows;
    hasChildren оставлен приоритетной подсказкой, чтобы правка не мешала
    будущему ленивому режиму.


--------------------------------------------------------------------------------
ПРАВКА 4. Колонка-экспандер treeExpanderColumn (новый экспорт)
--------------------------------------------------------------------------------
Файл: BaseTreeTable.tsx (добавлено в конец)

Добавлено:
    export const treeExpanderColumn = <TData,>(options?) => ColumnDef<TData>

    Параметры (все необязательные):
        accessorKey  поле узла, значение которого выводится рядом со стрелкой
                     (по умолчанию 'name')
        header       заголовок колонки (по умолчанию '')
        indent       отступ в px на каждый уровень вложенности (по умолчанию 20)
        id           id колонки (по умолчанию '__expander')

    Использование:
        columns={[
            treeExpanderColumn({ accessorKey: 'nm', header: 'Наименование' }),
            ...остальные колонки
        ]}

Почему:
    BaseTreeTable рисует только те ячейки, что описаны в columns. Ни кнопки
    раскрытия, ни отступа по row.depth среди них не было — раскрывать дерево
    было нечем, а уровни визуально не различались (именно это и создавало
    впечатление, что поддерживается один уровень вложенности). Раньше такую
    колонку писал у себя каждый потребитель; теперь она поставляется вместе
    с компонентом.

Детали реализации:
    - отступ считается как row.depth * indent, глубина ничем не ограничена;
    - в обработчике стрелки стоит e.stopPropagation(): без него клик всплывает
      до <td>/<tr> и заодно выделяет строку и вызывает handleRowClick;
    - у листьев вместо кнопки рендерится пустышка той же ширины, чтобы подписи
      листьев и веток были выровнены;
    - проставлены aria-label и aria-expanded.


--------------------------------------------------------------------------------
ПРАВКА 5. Безусловный вызов setIsLeaf
--------------------------------------------------------------------------------
Файл: BaseTreeTable.tsx

Было:
    setIsLeaf(!row.original.hasChildren);

Стало:
    if (setIsLeaf){
        setIsLeaf(!row.getCanExpand());
    }

Почему:
    - setIsLeaf объявлен в пропсах как необязательный (setIsLeaf?: any), но
      вызывался безусловно — без этого пропса компонент падал на первом же
      клике по строке;
    - признак листа берётся у строки, а не у поля hasChildren: при полной
      загрузке дерева этого поля может не быть вовсе, и тогда любой узел
      считался бы листом.

ЧТО НЕ МЕНЯЛОСЬ

    - хук fetchChildren и логика updateNode в useFetchTreeData.tsx — не

================================================================================
ПРОВЕРКА
================================================================================
    - tsc (TypeScript 5, react-jsx, @tanstack/react-table 8, @types/react 18) —
      ошибок нет;
    - прогон логики раскрытия на @tanstack/table-core 8.21.3, дерево 4 уровней,
      без поля hasChildren:

        свёрнуто:  Корень [+]
        раскрыт корень:
                   Корень [+] / A [+] / B
        раскрыт A: Корень [+] / A [+] / A1 [+] / A2 / B
        раскрыт A1:Корень [+] / A [+] / A1 [+] / A1a / A2 / B
        максимальная достигнутая глубина row.depth = 3
        toggleAllRowsExpanded() -> expanded = true, без исключения

      [+] отмечены строки, у которых getCanExpand() = true; листья (B, A2, A1a)
      корректно не раскрываются.


================================================================================
ЧТО НУЖНО СО СТОРОНЫ БЭКЕНДА
================================================================================
    Эндпоинт должен вернуть либо один корневой объект, либо массив корней,
    у каждого узла — поле children с массивом потомков (вложенность любая):

        [{ "id": 1, "nm": "...", "children": [
             { "id": 2, "nm": "...", "children": [ ... ] },
             { "id": 3, "nm": "..." }
        ]}]

    Поле hasChildren необязательно.

    Если исходные данные — плоский adjacency-list (id / parent / nm, корни
    помечены parent = 0), собрать вложенную структуру нужно либо в сервисе,
    либо на клиенте перед передачей в компонент. Хелпер сборки дерева из
    плоского списка в этот патч не входит.
